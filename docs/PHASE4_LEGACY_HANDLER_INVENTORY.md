# Phase 4 legacy handler inventory

This inventory describes the current local implementation. It distinguishes conversational decisions from provider and session operations. A validated `ConversationControlPlane` decision is the authority for interpreted turns; the compatibility tail in `ConversationMessageService` remains for un-interpreted deterministic commands and test fixtures.

| Component and entry point | Classification | Current disposition |
| --- | --- | --- |

| `ConversationMessageService.handleExplicitServiceSwitch`, `routeActiveConversation`, `mapOrchestrationPlanToLegacyDecision` | Duplicate conversational decision-making | Retired for interpreted production turns. They remain reachable for un-interpreted commands and low-confidence compatibility fixtures with the test-only flag. Their keyword-to-flow logic must be removed after the remaining command cases are covered by the control plane and executor tests. |

## Configuration and migration boundary

`LEGACY_CONVERSATION_ROUTING_FALLBACK` defaults to `false` in `.env.example`. `assertLegacyRoutingConfiguration` rejects `true` in development, staging and production at startup. The only enabled case is `NODE_ENV=test`, where existing low-confidence compatibility fixtures still exercise legacy behavior. A validated interpreted production turn returns through the control-plane decision, approved form gate or registered workflow executor before the legacy decision tail.

The remaining migration order is: (1) cover deterministic result and form-resend commands in each vertical; (2) move form token/session operations and validated search launches into existing services/executors; (3) retire the keyword switch and legacy plan mapping; (4) remove the unused `ConversationManager` export after downstream API review. Preserve provider rendering, background jobs, pagination and idempotency throughout.

## Verification boundary

Unit and route tests use application services and provider doubles. They verify routing, state reconciliation and form behavior, but do not prove live WhatsApp/provider delivery or production deployment configuration.

## Phase 5 migration checkpoint

The inventory above remains the full retirement map. Verified ownership changes in this checkpoint:

| Functionality | Previous location | Current owner | Retired code |
| --- | --- | --- | --- |
| Pausing competing durable journeys | Duplicate `clearCompetingSearchSessions` functions in `forms.ts` and `ConversationMessageService.ts` | `ConversationControlPlane.pauseCompetingWorkflows`, using the five existing session services | The form-route copy of `clearCompetingSearchSessions` and both copies of its five-service pause loop. The conversational wrapper remains for hotel-intake cleanup. |
| Selecting the next displayed result batch | Four repeated branches in the active hotel, restaurant, excursion and logistics handlers | `SearchFlowEngine.nextPage`; each vertical retains its renderer and channel delivery | Four duplicate batch-index and offset calculations. |
| Dispatching a validated provider search | Flow switch inside `ConversationMessageService.executeValidatedSearch` | The existing `WorkflowExecutorRegistry`, with a search-execution branch in each registered vertical executor | The five-way search execution switch. The shared wrapper now dispatches the backend-validated plan to the allow-listed registry. |
| Mapping selected excursion and transport booking forms into pending requests | `forms.submitFormCore` branches | `ExcursionSearchSessionService.submitBookingForm` and `LogisticsSearchSessionService.submitBookingForm` | Route-level request mapping and direct `saveProviderPending` calls. The route still authenticates and validates the form, checks the selected workflow, stores the service request and renders a truthful confirmation. |

The shared runtime sequence is: channel adapter → canonical event acceptance and idempotency → `ConversationControlPlane`/`Orchestrator` → `DecisionEngine` validation → existing flow/session services and registered active workflow executors → durable session write and Redis projection → channel renderer/delivery. A submitted form enters the canonical processor under a workflow lock after token, CSRF and revision checks; its validated business effects use the existing session services.

**At the Phase 5 checkpoint, still requiring migration:** background search delivery and result rendering in `ConversationMessageService`; form token generation and the five form gates; itinerary generation and workspace effects in `forms.submitFormCore`; deterministic result commands inside the five active vertical handlers; the test-only keyword router and legacy plan mapping; and the exported but runtime-unused `ConversationManager`. The Phase 5B section below updates this status.

## Phase 5B checkpoint

| Area | Verified migration or boundary | Remaining work |
| --- | --- | --- |
| Background hotel, restaurant, excursion and transport search | Result delivery now supplies a session/revision continuation check to each WhatsApp outbound adapter. Text and voice replies honor that check; failure replies are suppressed after a workflow revision or stage change. The duplicate excursion `saveResults` call for empty results was removed. Provider sends are not retried after an ambiguous delivery outcome. Website chat searches return the saved result in the HTTP reply instead of launching a WhatsApp-only background delivery. | Background search orchestration and card rendering remain in `ConversationMessageService`. Website push delivery and a persistent delivery queue are not established by this change. Live provider delivery is unverified. |
| Five form gates | `WorkflowFormService.openWorkflowForm` now owns token issue, profile context, competing-workflow pause, form-session writes and form response assembly for hotel, restaurant, excursion, logistics and itinerary. The five old gates retain only restore/resend and test compatibility checks before delegating. A validated `send_form` decision opens the form; an explicit booking switch with a valid schema proposal receives that backend decision. | The thin compatibility gates remain in `ConversationMessageService` because test fixtures still exercise keyword entry and existing restore/resend behavior. Their remaining keyword checks must be retired after equivalent decision-path coverage exists. |
| Itinerary form effects | `ItineraryWorkspaceService.generateFromSubmittedForm` owns the submitted itinerary's session transitions, planning and workspace creation. `forms.submitFormCore` keeps token, CSRF, canonical-event, revision, criteria and service-request validation, then calls that method. | Route still owns completion rendering and delivery. The planner and workspace writes are not one database transaction; retry behavior after a partial failure needs a separate durable execution design. |
| Deterministic commands | Existing explicit reset, result selection, pagination and booking-request commands remain behind the shared state and executor path. The itinerary executor no longer interprets `execute_search` as permission to open a form. | Text-command parsing inside active vertical handlers remains. The test-only keyword compatibility branch remains until equivalent decision-path coverage exists. |
| `ConversationManager` | No production caller of `getConversationManager` or `createMessage` exists under `src`; `src/services/index.ts` still exports the service. | Retained as an exported compatibility API until downstream consumers can be checked. It is not a live state owner in the current runtime. |

The current delivery sequence is canonical ingress → validated control-plane decision → registered workflow executor → search flow service → optimistic session `saveResults` → WhatsApp renderer and outbound adapter with a current-session check, or a synchronous website chat reply. A workflow pause, switch or revision change invalidates a pending result before the next WhatsApp adapter send. These checks cannot recall a message already accepted by a provider.
